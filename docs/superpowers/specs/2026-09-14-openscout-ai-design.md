# OpenScout AI：开源 AI 产品情报 Copilot 设计规格

## 1. 项目摘要

OpenScout AI 是一个基于 DocsGPT 二次开发的开源产品情报工具。它将公开 GitHub 仓库中的文档、Issues、评论和 Releases 转换为可检索、可统计、可追溯的产品情报，帮助产品经理快速完成竞品研究、社区反馈分析和版本演进梳理。

项目优先服务简历作品集目标，同时保留真实推广路径。整个交付分为两个阶段：阶段 A 在 15 个工作日内完成可演示、可评估的作品集版本；阶段 B 再用 5 至 7 个工作日增加任意公开仓库接入、增量同步和可分享报告。

DocsGPT 是项目底座，负责已有的认证、聊天、模型调用、文档管理、向量检索和基础界面。OpenScout AI 的原创工作集中在 GitHub 数据接入、产品情报数据模型、查询路由、结构化统计、证据化输出、对照实验和产品化界面。项目说明和简历中必须如实披露这一边界。

## 2. 价值假设

### 2.1 目标用户

- 研究 AI 开源产品的产品经理和产品运营人员。
- 需要跟踪竞品变化的创业者、战略分析人员和开发者关系人员。
- 希望从社区反馈中识别产品机会的开源项目维护者。

### 2.2 核心问题

开源产品信息分散在 README、仓库文档、版本记录和大量 Issues 中。人工研究需要在多个项目之间切换，阅读成本高，统计口径难以保持一致，结论也难以追溯到原始证据。

### 2.3 产品价值

OpenScout AI 将一次完整研究压缩为一条可验证的工作流：选择产品、提出问题、查看统计和证据、横向比较、生成报告。系统将确定性统计与生成式分析分开，减少模型凭空计数和过度推断。

### 2.4 价值边界

GitHub Issues 主要代表开发者和活跃社区成员，不能替代销售记录、商业客户访谈或完整市场调研。产品输出统一使用“开源社区信号”“产品机会线索”等表述，不把 Issue 数量直接解释为商业优先级。

## 3. 范围

### 3.1 阶段 A：简历作品集版本

初始研究对象固定为以下三个公开仓库：

- `langgenius/dify`
- `infiniflow/ragflow`
- `labring/FastGPT`

初始数据窗口为 2025-09-14 至 2026-09-14；此后按滚动 12 个月理解。数据包括：

- 默认分支的 README 和仓库内 `docs/` 文档。
- 数据窗口内发布的 Releases。
- 数据窗口内创建或更新的非 Pull Request Issues，每个仓库最多保留最近 1,000 条。
- 每条 Issue 最多保留按创建时间排序的前 20 条评论。

如果达到数据上限，界面必须显示实际覆盖范围，所有趋势指标只针对已收录数据计算。

阶段 A 必须提供：

- 带产品、时间、来源过滤的证据化问答。
- 产品功能和社区信号对比矩阵。
- Issue 主题聚类和趋势统计。
- 带事实、统计、推断区分的产品洞察报告。
- 至少三组 RAG 对照实验及可复现结果。
- Markdown 和 PDF 报告导出。

### 3.2 阶段 B：可推广版本

阶段 B 增加：

- 用户输入任意公开 GitHub 仓库地址并创建情报空间。
- 按外部对象更新时间执行增量同步。
- 生成可分享的只读报告链接。
- 展示每次同步状态、数据覆盖和失败原因。
- 邀请 5 至 10 名目标用户完成真实研究任务并记录结果。

### 3.3 非目标

- 不采集社交媒体、新闻、封闭社区或商业数据库。
- 不根据社区数据自动决定产品路线图。
- 不开发支付、企业多租户或复杂权限系统。
- 不从零重写 DocsGPT 已具备的聊天、模型接入和文档管理能力。
- 不用 GraphRAG 处理所有问题，也不让 LLM 直接完成精确统计。

## 4. 系统架构

### 4.1 基础设施

沿用 DocsGPT 的后端、前端和任务执行方式：

- DocsGPT Python 后端承载 API、检索和业务编排。
- React/Vite 前端承载情报工作台和报告界面。
- PostgreSQL 作为结构化数据存储，pgvector 保存向量索引。
- Redis 和 Celery 执行采集、解析、Embedding、GraphRAG 和增量同步任务。
- 现有 DocsGPT LLM、Embedding、Retriever 和 Vector Store 抽象保持不变，新增能力通过窄接口接入。

### 4.2 模块边界

#### GitHub 连接器

负责读取仓库内容、Issues、评论和 Releases，处理分页、API 限流、断点续传和增量游标。连接器只返回标准化前的外部记录，不承担切片、检索或洞察生成。

#### 标准化与元数据模块

将不同 GitHub 对象转换成统一情报文档。标准字段包括：

- `repository`
- `source_type`: `documentation`、`issue`、`issue_comment` 或 `release`
- `external_id`
- `title`
- `body`
- `source_url`
- `state`
- `labels`
- `comments_count`
- `reactions_count`
- `version`
- `created_at`
- `updated_at`
- `published_at`
- `retrieved_at`
- `content_hash`

`repository + source_type + external_id` 是幂等键。`content_hash` 未变化时不重新切片和生成 Embedding。

#### 索引模块

一份标准情报文档进入三类存储：

- PostgreSQL 保存原始内容、状态、日期、标签和统计字段。
- 向量与 BM25 索引用于混合检索。
- GraphRAG 索引用于关系型、多跳问题。

GraphRAG 只对 README、仓库文档、Releases，以及每个仓库最多 300 条高信号 Issues 建图。高信号 Issue 按评论数和 reactions 的归一化组合排序。GraphRAG 数据不得用于计算 Issue 数量或趋势，以免抽样偏差进入统计结论。

#### 查询路由模块

路由器输出 `intent`、产品范围、时间范围、来源类型和检索策略。意图包括：

- `factual`: 混合检索后 Rerank。
- `temporal`: 元数据时间过滤后混合检索和 Rerank。
- `comparative`: 按产品拆分子查询，分别检索后合并。
- `aggregate`: 使用 SQL 计算结果，再检索代表性证据。
- `relational`: 使用 GraphRAG；不可用时回退混合检索。

路由器置信度低于 0.65 时使用混合检索默认路径，不自动启动高成本 GraphRAG。

#### 洞察生成模块

接收结构化统计和检索证据，生成结论、解释和报告。输出中的每个事实性主张都必须关联至少一个证据标识。没有证据支持的内容只能标记为“AI 推断”，不能作为事实展示。

#### 展示模块

在 DocsGPT 现有体验上增加情报首页、分析工作台、证据面板、竞品矩阵、报告页和阶段 B 仓库接入页。新页面复用现有 Redux、组件和样式体系，不进行无关的全局 UI 重构。

## 5. 数据流

### 5.1 首次同步

1. 用户或预置任务选择仓库和时间窗口。
2. GitHub 连接器按数据类型分页获取对象。
3. 标准化模块过滤 Pull Requests、清洗 Markdown 并写入幂等记录。
4. 文档按来源类型切片，写入向量和 BM25 索引。
5. 高信号子集异步构建 GraphRAG。
6. 系统记录对象数、时间覆盖、失败数和最后成功同步时间。

### 5.2 增量同步

1. 使用上次成功同步时间作为增量游标。
2. 获取新增或更新对象。
3. 比较 `content_hash`，只重建变化内容的索引。
4. 删除状态不明的对象先标记为待核对；连续两次同步确认不存在后从活跃索引移除，但保留审计记录。
5. 同步部分失败时提交成功批次，并记录可重试失败项。

### 5.3 查询

1. 解析用户问题和界面过滤条件。
2. 查询路由器选择统计、检索、GraphRAG 或组合路径。
3. 对候选证据执行 Rerank 和去重。
4. 将结构化数据与证据交给洞察生成模块。
5. 校验事实性主张是否存在引用。
6. 返回答案、证据、可信度、数据覆盖和检索追踪信息。

## 6. 产品体验

### 6.1 情报首页

每个产品卡片展示已收录文档、Issues、Releases 数量，数据覆盖时间，最近同步时间，最近版本和近期高频反馈主题。达到采集上限或存在同步失败时，卡片必须显示覆盖警告。

### 6.2 分析工作台

工作台提供产品多选、时间范围、数据来源、问题类型和推荐问题。用户可以直接自然语言提问；显式过滤条件优先于模型解析出的隐式条件。

### 6.3 结果与证据

结果按以下顺序展示：

1. 一句话结论。
2. 结构化分析。
3. 确定性统计。
4. 原始证据。

每条证据显示来源类型、仓库、日期、版本、摘要和 GitHub 链接。每条结论标记为“事实”“统计”或“AI 推断”，并显示低、中、高可信度。可信度不使用模型的自报分数，而采用以下确定性规则：有官方文档或 Release 直接支持且无冲突，或来自覆盖完整的 SQL 统计时标记为高；只有至少两个不同作者的 Issue 相互印证且无官方来源时标记为中；只有单个 Issue、存在来源冲突、数据已过期或结论属于 AI 推断时标记为低。多条结论分别计算可信度，不为整篇回答生成一个笼统分数。

### 6.4 竞品对比

矩阵按功能维度展示三个产品的支持状态、发布时间、社区信号数量和代表性证据。每个单元格必须可以展开查看来源。没有足够证据时显示“尚未确认”，不得用空白或模型常识补齐。

### 6.5 产品洞察报告

报告包括执行摘要、功能对比、反馈趋势、产品机会线索、风险与证据限制、完整来源列表。阶段 A 支持 Markdown 和 PDF；阶段 B 增加可分享的只读链接。

### 6.6 五分钟演示路径

1. 从首页发现一个社区反馈趋势。
2. 打开统计和代表性 Issues。
3. 提问该问题与最近 Release 的关系。
4. 横向比较三个产品。
5. 生成带证据的产品洞察报告。

## 7. 评估设计

### 7.1 数据集

建立 80 条人工审核问题，其中事实、时间、对比、综合问题各 20 条。每类取 15 条作为开发集、5 条作为保留测试集。每条记录包含：

- 问题和类型。
- 标准答案要点。
- 正确证据 URL。
- 适用仓库和时间范围。
- 可接受答案规则。

LLM 可以生成候选问题，但人必须核验问题、答案和证据。保留测试集在方案确定前不得用于调参。

### 7.2 对照实验

必须完成并保存以下实验：

1. 仅向量检索与混合检索对比。
2. 混合检索与混合检索加 Rerank 对比。
3. 统一 RAG 与查询路由对比；复杂问题分别走 SQL 或 GraphRAG。

所有实验固定数据快照、问题集、模型版本和主要参数。实验结果保存为机器可读数据和面向作品集的摘要。

### 7.3 指标与门槛

记录 Recall@5、nDCG@10、答案正确率、引用准确率、忠实度、平均响应时间和单次查询 Token 成本。

阶段 A 发布门槛：

- 事实题正确率不低于 80%。
- 引用准确率不低于 90%。
- 对比和综合问题成功率不低于 75%。
- 非 GraphRAG 普通问题平均响应时间不超过 10 秒。
- 五个固定演示场景不存在无引用的事实性主张。

若绝对门槛未达到，产品仍可作为实验项目保留，但不能在 README 或简历中声称达到该指标。最终简历只使用实际测量值。

## 8. 异常处理与可信性

- GitHub API 限流：遵守响应头，使用指数退避和断点续传，不进行无界重试。
- 单来源失败：记录错误并继续其他来源；界面显示部分完成。
- 数据变更或删除：保留更新时间和审计状态，增量同步修正活跃索引。
- GraphRAG 未完成或失败：回退混合检索，并在检索追踪中标记回退。
- 证据不足：回答“当前收录数据无法支持该结论”，同时展示相关但不足的证据。
- 来源冲突：同时展示冲突结论、来源和日期，不自动选择对产品更有利的一方。
- 数据过期：结果顶部显示最后同步时间和覆盖窗口。
- LLM 输出无引用：最多重新生成一次；仍失败则降级为证据列表和结构化统计。
- 导出失败：保留报告草稿，允许用户重新导出，不重复运行完整检索。

## 9. 测试策略

- 单元测试覆盖 GitHub 对象转换、幂等键、时间过滤、路由规则、可信度计算和指标计算。
- 连接器使用录制或固定响应测试分页、限流、部分失败和删除对象。
- 集成测试覆盖从标准化样本到索引、查询、引用和报告生成的完整链路。
- 回归测试对固定开发集运行，指标下降超过 5 个百分点时阻止合并。
- 保留测试集只用于里程碑验收和最终结果。
- 五个演示场景在发布前重复运行并保存结果。
- 阶段 B 进行 5 至 10 名目标用户的任务测试，记录任务完成率、完成时间、证据点击和报告采纳意愿。

## 10. 四周交付路线

### 第 1 周：底座、数据与基线

- 运行 DocsGPT 并理解现有 RAG 链路。
- 完成三个仓库的数据接入和元数据模型。
- 建立基础向量检索和首批 20 条测试题。
- 产出系统基线、数据字典和第一次评估。

学习重点：RAG 链路、Chunk、Embedding、向量数据库和元数据过滤。

### 第 2 周：检索优化

- 增加 BM25、混合检索、Rerank、时间和版本过滤。
- 将评估集扩展到 80 条并锁定 20 条保留测试题。
- 完成前两组对照实验。
- 产出可复现的检索优化报告。

学习重点：稀疏与稠密检索、Recall@K、nDCG、Rerank，以及检索错误与生成错误的区别。

### 第 3 周：产品智能和阶段 A 发布

- 增加查询路由、SQL 统计和选择性 GraphRAG。
- 完成首页、工作台、证据面板、竞品矩阵和报告导出。
- 完成异常回退、回归测试和五分钟演示。
- 发布可写入简历的阶段 A 版本。

学习重点：Query Routing、Temporal RAG、GraphRAG、可信 AI、成本与延迟权衡。

### 第 4 周：阶段 B 和作品集

- 增加任意公开仓库接入、增量同步和分享报告。
- 完成目标用户测试并记录实际结果。
- 完成公开部署、README、演示视频、架构说明、简历描述和面试问答。

学习重点：用户验证、产品指标、上线取舍和迭代决策。

每天 6 至 8 小时建议分配为：45 至 60 分钟概念学习、4 至 5 小时 AI 辅助实现、1 至 1.5 小时实验与失败分析、30 分钟产品决策和面试表达记录。

## 11. 完成定义

### 阶段 A 完成

- 三个预置仓库在界面中显示明确的数据覆盖和同步状态。
- 用户可以完成事实、时间、对比、聚合和关系型问题。
- 所有事实性结论可展开原始证据。
- 三组对照实验可复现，实际指标写入结果文件。
- 五分钟演示路径稳定通过。
- README 明确说明 DocsGPT 底座、OpenScout AI 的新增能力、系统限制和真实指标。

### 阶段 B 完成

- 用户可以输入任意有效的公开 GitHub 仓库并完成首次同步。
- 增量同步不会为未变化内容重复建索引。
- 报告可通过只读链接分享。
- 至少 5 名目标用户完成测试，原始反馈和统计结果可供复盘。
- 简历和面试材料只使用真实实现、真实实验和真实用户数据。

## 12. 作品集叙事

项目叙事采用以下结构：发现开源产品情报整理效率问题；设计基于公开 GitHub 数据的可追溯方案；在 DocsGPT 上新增连接器、结构化统计和查询路由；通过三组实验优化检索质量；用真实用户任务验证效率和可信度。

最终材料必须包含：产品问题定义、范围取舍、架构与数据流、实验表格、失败案例、迭代决策、五分钟演示视频、在线体验地址，以及对 GitHub Issues 数据偏差的明确说明。
