# OpenScout AI 实施计划总索引

> **供智能执行代理使用：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`，逐项执行本计划。所有步骤均使用复选框（`- [ ]`）跟踪状态。

**目标：** 将 OpenScout AI 分成两个可独立发布的阶段执行，先完成具备简历价值的阶段 A，再投入时间开发推广能力。

**架构：** 阶段 A 构建固定三个仓库的产品情报工具，并用实验验证检索质量。阶段 B 复用该垂直功能链路，扩展任意公开仓库、增量同步、报告分享和用户验证。两份详细计划均给出精确文件、接口、测试、命令和提交边界。

**技术栈：** Python 3.12、Flask-RESTX、SQLAlchemy Core、Alembic、PostgreSQL/pgvector、Redis/Celery、Pydantic 2、pytest、React/TypeScript、Redux Toolkit、Vite/Vitest、ReportLab。

**规格：** `docs/superpowers/specs/2026-09-14-openscout-ai-design.md`

## 全局约束

- 完成并测量阶段 A 后，才能开始阶段 B。
- 复用 DocsGPT 现有认证、LLM、Embedding、HybridRetriever、GraphRAG、向量存储、Redis/Celery、Redux 和组件规范。
- OpenScout 原创能力必须限制在独立的 `intelligence` 功能边界内，并在作品集中披露 DocsGPT 底座。
- 遵循红绿 TDD；每个可审阅任务独立提交；所有指标只使用真实测量值。

## 已解决的审阅问题

1. 旧计划按日期组织，而不是按可独立测试的交付物组织。新计划拆成 22 个可审阅任务，每个任务都有红绿测试和独立提交。
2. 旧计划只列文件，没有定义共享接口。阶段 A 现在会先冻结 `QueryResult`、`Evidence`、`Claim`、`Coverage`、`RouteDecision` 和 `SyncSummary`，再开发调用方。
3. 旧报告设计可能错误复用 DocsGPT Artifact，但当前 Artifact 表强制要求会话或工作流父对象。新计划使用产品领域专属的 `intelligence_reports` 表。
4. 旧计划把 Rerank 当成现成功能，但仓库中只有预留配置。新计划增加与服务商无关的 `Reranker` 协议和经过测试的无操作回退，同时不暗中引入重量级依赖。
5. 旧增量删除设计可能在 GitHub 部分失败后误删数据。阶段 B 只在某类数据完整同步后累计缺失次数，并要求连续两次成功同步确认缺失。
6. 旧评估顺序到后期才扩充数据集。阶段 A 现在会在优化前冻结 60 条开发题和 20 条封存题，并禁止运行后修改封存题。
7. 前后端字段可能漂移。新计划先定义后端契约，TypeScript 严格复用相同的 snake_case 响应字段。
8. 规格中的可信性规则已经变成可执行要求：逐结论引用、确定性可信度、最多一次重新生成、拒答/降级证据响应和冲突保留都有对应测试。

## 每日学习规则

每天仅用 45—60 分钟学习当前任务所需概念；用 4—5 小时借助 AI 实现；用 1—1.5 小时运行实验并分析失败；用 30 分钟记录一项产品决策和两分钟面试表达。目标不是记忆语法，而是能解释产品取舍并验证 AI 生成的实现。
